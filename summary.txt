AI Code Editor — Phase 2: Real Local File System Access
================================================================================

STATUS: complete. `cd client && npm run dev`, then open http://localhost:5173

--------------------------------------------------------------------------------
WHAT CHANGED (high level)
--------------------------------------------------------------------------------
Phase 1 read from a hard-coded dummy tree. This phase replaces that with the
browser's File System Access API, so clicking "Open Folder" gives the editor
real read/write access to a folder on the user's laptop.

The dummy tree was NOT deleted. It now acts as an offline fallback: it is shown
until a real folder is opened, and the explorer displays a notice telling the
user to click "Open Folder". Once a folder is opened, the dummy tree is
discarded permanently for that session.

NEW FILES
--------------------------------------------------------------------------------

1. client/src/services/fileSystemAccess.js
   The only module that touches the File System Access API.

   HANDLE REGISTRY
   FileSystemHandle objects are not serializable, so they are never put in
   Redux. They live in a module-level Map:

       registry: id -> { handle, parentId, name, type }

   Redux only ever stores plain data: { id, name, type, children, isOpen }.

   - isFileSystemAccessSupported()  -> true when 'showDirectoryPicker' in window
   - getHandleById(id)              -> the FileSystemHandle for a node id
   - getRegistryEntry(id)           -> { handle, parentId, name, type } or null
   - getParentHandle(id)            -> parent directory handle (null for root)
   - registerHandle(handle, meta)   -> stores a handle under a new uuid and
                                       returns the plain Redux node. Passing an
                                       existing `id` rebinds that slot, which is
                                       how a rename keeps its open tab.
   - forgetHandles(ids)             -> drops stale registry entries

   PERMISSIONS
   - requirePermission(handle, mode = 'readwrite')
       queryPermission() first, then requestPermission() if not granted, and
       throws if the user declines. Called before every write operation.
       Must run from a user gesture for the browser to show its prompt.

   READING
   - openFolder()
       window.showDirectoryPicker({ id: 'code-matrix' }), stores and returns the
       root DirectoryHandle. Called with no arguments before any other await so
       the picker keeps its user activation.
   - readDirectoryTree(directoryHandle)
       Recursively walks a directory with its async iterator
       (for await (const [name, handle] of directoryHandle.entries())), returning
       a nested node { id: crypto.randomUUID(), name, type, isOpen, children }.
       Resets the registry. The root is returned expanded. Entries are sorted
       folders-first, then alphabetically by name.
   - reindexDirectory(directoryHandle, previousNode)
       Re-reads a directory that was just renamed, reusing the ids of entries
       that still exist so open tabs and unsaved buffers survive the rename.
   - readFileContent(fileHandle)
       fileHandle.getFile(), then .text().

   WRITING
   - writeFileContent(fileHandle, content)
       createWritable(), write(content), close() (close runs in a finally block
       so a failed write cannot leave the stream open).
   - createNewFile(parentDirectoryHandle, fileName)
       parentDirectoryHandle.getFileHandle(fileName, { create: true })
   - createNewFolder(parentDirectoryHandle, folderName)
       parentDirectoryHandle.getDirectoryHandle(folderName, { create: true })
   - deleteEntry(parentDirectoryHandle, name, type)
       parentDirectoryHandle.removeEntry(name, { recursive: type === 'folder' })
       (`recursive` is only passed for folders, matching the API's contract.)
   - renameEntry(parentDirectoryHandle, oldName, newName, type)
       The API has no atomic rename, so this is copy + delete:
         * file   -> read the source File blob, write it to the new entry, then
                     remove the old entry. Writing the blob (not text) keeps
                     binary files byte-for-byte intact.
         * folder -> copyDirectory() recurses through every entry, then removes
                     the original directory with { recursive: true }.
       Returns the handle of the new entry.

   SCAN SCOPE
   - SKIP_DIRECTORIES = new Set(['node_modules', '.git'])
     These are skipped at every level while walking. Without this, opening a
     typical JS project freezes the tab and produces an unusable tree. Delete or
     extend this constant to change the behaviour.

2. client/src/hooks/useOpenFolder.js
   - openLocalFolder(): support check -> openFolder() -> readDirectoryTree() ->

   - returns { openLocalFolder, isOpening, isSupported } so the button can show a

   - success                 -> markSaved() + "Saved <name>" toast

HOW THE PIECES CONNECT NOW
--------------------------------------------------------------------------------
Topbar
  "Open Folder" -> useOpenFolder -> showDirectoryPicker -> readDirectoryTree ->
  loadWorkspace(tree). Save -> useSaveActiveFile -> writeFileContent(handle).

Sidebar
  Clicking a row -> Redux only (selection + expand/collapse + open tab).
  New / Rename / Delete -> real API calls -> Redux updated with the result.
  Every mutation is "disk first, then Redux", so the tree can never claim a file
  exists when it does not.

Editor
  Opening a tab -> getHandleById -> readFileContent -> setContent (clean buffer).
  Typing -> updateContent (marks unsaved).
  Ctrl+S / Save -> writeFileContent -> markSaved + toast.

Redux
  Holds serializable tree data, tab state and buffers. The handle registry lives
  outside Redux, keyed by the same node ids.

LIMITATIONS
--------------------------------------------------------------------------------

BROWSER SUPPORT
  Requires a Chromium browser (Chrome, Edge, Brave) on https or localhost.
  Firefox and Safari do not implement showDirectoryPicker. The app detects this
  and shows "Your browser doesn't support local folder access. Please use Chrome,
  Edge, or Brave." in both the explorer and the welcome screen. Everything still
  works in demo mode on those browsers.

SECURE CONTEXT
  crypto.randomUUID() and the File System Access API both need a secure context.
  The Vite dev server runs on http://localhost, which counts as secure, so this
  works out of the box in development. A production build must be served over
  HTTPS.

NO NATIVE RENAME
  The File System Access API has no rename/move operation. renameEntry() copies
  the entry and deletes the original, which means:
    - Renaming a large file or a folder with many files blocks the UI until the
      copy finishes; there is no progress indicator.
    - A rename is not atomic. If the tab is closed mid-copy, both the old and the
      new entry can exist on disk.
    - Metadata (timestamps) is not preserved. File contents are, including
      binary data.

PERMISSIONS ARE PER SESSION
  Write permission is granted per folder and is dropped on every page reload.
  Handles are intentionally kept in memory only and are never persisted to
  IndexedDB, so a refresh always requires picking the folder and granting access
  again. The first write to a folder triggers the browser's permission prompt.

SCAN SCOPE
  node_modules and .git are skipped at every level. Everything else is walked
  eagerly and fully on "Open Folder", so a very large or deeply nested directory
  can still take a while. There is also no file watcher: changes made to the
  folder by another program will not show up until the folder is reopened.

DEMO WORKSPACE
  Save, create, rename and delete in the demo workspace only touch Redux. Nothing
  is written to disk, and the changes are lost on refresh.

BUFFERS AND UNSUPPORTED FILES
  readFileContent() decodes files as UTF-8 text. Opening a binary file (image,
  archive, compiled artefact) will show mojibake; it will not be corrupted unless
  you save it, which would replace the binary with text.

--------------------------------------------------------------------------------
ARCHITECTURE / WHY IT IS SHAPED THIS WAY
--------------------------------------------------------------------------------
Replit free-tier Autoscale has an EPHEMERAL disk: server/workspaces is wiped
whenever the server sleeps or restarts. Consequences baked into the design:
  - MongoDB stores ONLY metadata (Project.model.js: projectId, name, ownerId,
    diskPath, lastAccessedAt). Never file contents.
  - Files live temporarily at server/workspaces/<projectId>/ on disk.
  - The UI warns the user repeatedly and pushes them to export.
  - Every workspace route checks the folder exists and answers 404
    WORKSPACE_MISSING when it does not.

REDUX TREE IDS ARE PATHS
For a cloud project every tree node's `id` is its workspace-relative path (the
root keeps the literal id "root"). This means tab ids, editor buffer keys and API
arguments are all the same string, so no id<->path map is needed. Demo-mode nodes
keep their old random ids.

THE TWO IMPORTANT LIMITATION BEHAVIOURS

1. TEMPORARY STORAGE:
   StorageNotice.jsx shows a dismissible amber banner ("This is temporary cloud

   with a "Re-import project" button that resets to demo and reopens the import
   picker. This also covers the reload path: useRestoreWorkspace() reopens the
   saved project and a 404 there shows the same recovery banner.

--------------------------------------------------------------------------------
1. ROOT CAUSE OF "Could not reach the server at http://localhost:4000"
--------------------------------------------------------------------------------
The server was NOT down and the port was NOT wrong. server.js started and
listened on the PORT from server/.env (4000), health answered, and register
returned 201 + a JWT when called with curl. The failure was CORS:

  server/.env had:  CLIENT_ORIGIN=http://localhost:5173/   <- trailing slash
  browser sends:    Origin: http://localhost:5173          <- no slash

The `cors` package compares origins as exact strings, so the mismatch meant
Access-Control-Allow-Origin was NEVER emitted. The browser then blocked every
response from http://localhost:4000, `fetch` rejected with a TypeError, and
api.js's catch-all re-threw it as the misleading message "Could not reach the
server at http://localhost:4000. Is it running?" — which sent everyone chasing
a server that was running fine. (A CORS failure and a real network failure look
identical to fetch(); the message is inherently a guess.)

FIXES
  - server/.env: CLIENT_ORIGIN=http://localhost:5173 (slash removed).
  - server/src/config/env.js: resolveCorsOrigin() now strips trailing slashes
    from every configured origin, so this exact bug cannot recur.
  - server/.env: PORT= 4000 -> PORT=4000 (worked via Number(), but fragile).
  - Server restarted; verified with curl that Origin: http://localhost:5173 now
    gets Access-Control-Allow-Origin: http://localhost:5173 on simple requests,
    on the OPTIONS preflight, and on /api/auth/* responses.

1. NODE-PTY CRASH ON WINDOWS (TypeError: ... reading 'forEach')
--------------------------------------------------------------------------------
ROOT CAUSE (confirmed by reading the installed source and by a deterministic
A/B reproduction, not just the reported stack trace):

  node_modules/node-pty/lib/windowsPtyAgent.js, ConPTY kill path:

      this._getConsoleProcessList().then(function (consoleProcessList) {
          consoleProcessList.forEach(...);      // <-- TypeError when undefined
      });

  ...and the helper it forks, conpty_console_list_agent.js:

      var consoleProcessList = getConsoleProcessList(shellPid);
      process.send({ consoleProcessList: consoleProcessList });

  getConsoleProcessList() returns `undefined` once the shell process has
  already exited (the console is gone). The parent then calls .forEach on that
  undefined value INSIDE a `.then()`, which is an UNHANDLED PROMISE REJECTION —
  and Node treats those as fatal, so the whole server process aborts. That is
  exactly the reported crash, and it only exists on the ConPTY path.

FIXES
  a) server/package.json: node-pty range bumped ^1.0.0 -> ^1.1.0 and
     `npm install` re-run. NOTE: 1.1.0 IS the latest published stable release
     (npm dist-tags latest = 1.1.0; the only newer builds are 1.2.0-beta.*), so
     upstream has not fixed this yet and the workaround below is required.
  b) terminalManager.js createTerminalSession(): spawn options now include
         ...(process.platform === 'win32' ? { useConpty: false } : {})
     On Windows this forces node-pty onto the older, stable winpty backend,
     which uses a SYNCHRONOUS native getProcessList() and never runs the
     crash-prone ConPTY code above. Linux/macOS keep node-pty's defaults.
  c) Crash-proof kill paths. killTerminal() deletes the session from the map
     FIRST, then wraps ptyProcess.kill() in try/catch and logs
     "[terminal] kill(<id>) failed (session dropped anyway): ..." instead of
     letting the throw escape. killTerminalsForSocket() and killAllTerminals()
     now log failures too (they used to swallow them silently), and
     writeToTerminal() is guarded the same way. The session is always removed
     from the sessions map regardless of what kill() does.

PROOF — deterministic A/B against the real node-pty code (forcing the
undefined consoleProcessList that the exited-shell race produces):
  ConPTY  (useConpty: true)  -> CRASHED: TypeError: Cannot read properties of
                               undefined (reading 'forEach')
  winpty  (useConpty: false) -> SURVIVED (no crash, no unhandled rejection)
Also: a socket-level stress run did 12 kill-a-running-pty cases, 12

1. TERMINAL NUMBERS NOW REUSE FREED SLOTS (per shell type)
--------------------------------------------------------------------------------
Before, a single module-level counterRef in TerminalPanel.jsx incremented
forever: opening PowerShell 1, 2, 3, closing 1 and 2 and opening another one
gave "PowerShell 4". The counter never looked at what was actually open.

NEW RULE (both places compute the same thing)
  The number for a new terminal = the LOWEST positive integer that no
  currently-open terminal of that SAME shell type is using. Shells are counted
  independently: PowerShell, CMD and bash each keep their own sequence, so a CMD
  terminal never shifts PowerShell numbers and vice versa.

  components/Terminal/TerminalPanel.jsx
    - `counterRef` was DELETED.
    - + lowestFreeSeq(shell): walks every group's panes, collects `seq` values of
      panes whose `shell` matches, then returns the smallest integer >= 1 that is
      not in that set (`while (used.has(seq)) seq += 1`). The answer is computed
      FRESH on every create — nothing is cached and nothing only increases.
    - nextPane(requestedShell) calls lowestFreeSeq(shell) and builds the title
      `${shellLabel(shell)} ${seq}`. createTerminal() and splitActiveTerminal()
      both go through it.

  features/terminalSlice.js
    - + a module-level copy of lowestFreeSeq(groups, shell, excludeTerminalId).
      It exists because the number is allocated against the REQUESTED shell, but
      the server is the source of truth for what actually spawned (a fallback for
      an unavailable shell, or the platform default when the client had no shell
      list yet).
    - setTerminalShell(...) now: if the reported `shellId` differs from the
      pane's current shell, it switches `pane.shell` AND re-allocates `pane.seq`
      via lowestFreeSeq(..., terminalId) (excluding the pane itself), then
      retitles from `label + seq`. Without this, two panes could end up both
      labelled "PowerShell 1" after a server fallback.

  EXPLICIT TEST (the scenario from the request)
    open PowerShell 1 / 2 / 3 -> close 1 and 2 -> open another PowerShell
      => "PowerShell 1"  (the lowest free number, NOT 4).
    CMD numbering verified independently: CMD 1, CMD 2 -> close CMD 1 -> next
      CMD is "CMD 1", and the PowerShell numbering is unaffected by CMD panes.

2. CUT/COPY/PASTE — ROOT CAUSE AND FIX
--------------------------------------------------------------------------------
The dispatch chain itself was correct (Copy/Cut -> clipboardSlice
{ path, type, mode } -> Paste only rendered when clipboard.path is set -> on
click it calls the rename endpoint for a cut and /duplicate for a copy with the
FOLDER's own path as targetFolderPath). Two behaviours made it fail in practice:

  ROOT CAUSE 1 — a name collision was a hard error.
    copyPathInWorkspace() threw 409 ALREADY_EXISTS whenever the target folder
    already contained an item of that name. A copy ALSO kept the clipboard on
    purpose (VS Code behaviour), so the very common sequence "copy a file, paste
    it, paste it again" — or pasting an item back into a folder that already had
    it — hit a red error toast and the second paste looked like it did nothing.

    FIX (server/src/utils/workspaceManager.js)
      + uniqueNameInFolder(folderAbsolute, name): if the name is taken, the copy
        is written as "<base> (copy)<ext>", then "<base> (copy 2)<ext>",
        "<base> (copy 3)<ext>", … So a duplicate never overwrites and never
        fails — copying a.txt into a folder that already has a.txt produces
        a (copy).txt and leaves the original untouched. copyPathInWorkspace no
        longer throws ALREADY_EXISTS at all.

  ROOT CAUSE 2 — a stale clipboard.
    After a successful copy-paste the clipboard was left populated, so Paste kept
    being offered and repeating it reproduced the collision above.

    FIX (client/src/components/Sidebar/Sidebar.jsx — handlePaste)
      The clipboard is now cleared after ANY successful paste (cut or copy), so a
      second Paste does nothing until something new is cut/copied. It is cleared
      only AFTER the request resolves (via .unwrap()), so a FAILED paste keeps the
      clipboard and can be retried.

  Also confirmed correct (no change needed):
    - the paste target is the CLICKED FOLDER's own path (`folderNode.id`, '' for
      the workspace root) — never the source item's path or its parent;
    - a CUT is a real server-side MOVE via PATCH /rename, so the original is gone
      afterwards and nothing is duplicated;
    - a COPY is a real server-side POST /duplicate; the original stays put;
    - after either one the tree refetches (refreshWorkspaceTree) and the new item
      is visible immediately.

1. EXPLORER AUTO-REFRESHES WHEN THE FOLDER CHANGES ON DISK
--------------------------------------------------------------------------------

NEW server/src/utils/fileWatcher.js
  - One refcounted chokidar watcher per ACTIVE project:
      startWatchingProject(projectId, notify)  -> +1 ref (starts on first call)
      stopWatchingProject(projectId)           -> -1 ref (closes at zero)
      closeAllWatchers()                       -> server shutdown
  - Watches the project folder (getWorkspacePath) and listens to add / addDir /
    unlink / unlinkDir / change.

    therefore collapses into ONE refresh.

    addDir/unlinkDir still fires, but nothing inside is watched.
  - Defence in depth: the same ignore rules are ALSO applied to every incoming
    event before it can schedule a refresh, because a directory created AFTER the
    watcher started (npm install creating node_modules) can otherwise leak events
    for its children.
  - The watched root itself is never ignored (chokidar calls `ignored` for it;
    returning true there silently watches nothing).
  - If the project folder does not exist yet (fresh scratch workspace, import in
    progress) it watches the parent container instead and scopes events to the
    project path, so it starts reporting the moment the folder is created.

NEW server/src/socket/workspaceSocket.js
  client -> server:  workspace:watch   { projectId }  (project became active)

FIX: Import-time exclusion vs. workspace-tree display are now FULLY separate
================================================================================

STATUS: complete and verified.

THE BUG
The Explorer hid folders that physically exist on disk. After running
`npm install` in a project's terminal, node_modules existed on the server but
never appeared in the tree; the same was true of .git, dist, build, .next, etc.

ROOT CAUSE
There were TWO independent exclusion lists, and the tree walker wrongly reused
the import concept:

  1. client/src/services/fileSystemAccess.js
       const IMPORT_SKIP_DIRECTORIES = new Set(['node_modules', '.git', 'dist',
                                                'build', 'out', '.next', '.cache'])
     This was CORRECT — it filters what gets read off the user's LOCAL LAPTOP
     and uploaded during import.

  2. server/src/utils/workspaceManager.js
       const SKIP_DIRECTORIES = new Set(['node_modules', '.git'])
     ...used by walkDirectory(), which getWorkspaceTree() (the
     GET /api/workspace/:projectId/tree endpoint) is built on. This is the BUG:
     the tree-display walk was applying an exclusion filter at all. Any folder
     named node_modules or .git on disk was silently omitted from the tree, no
     matter how it got there (import, `npm install`, `git init`, `npm run build`,
     or any other terminal command).

THE FIX — two distinct, independent pieces of logic
  * IMPORT-TIME EXCLUSION (unchanged behaviour, clearer intent)
      client/src/services/fileSystemAccess.js
      - Constant renamed SKIP_DIRECTORIES -> IMPORT_SKIP_DIRECTORIES, with a
        comment stating it applies ONLY to readAllFilesFromDirectory() while
        uploading a folder from the laptop. node_modules, .git, dist, build,
        out, .next and .cache continue to be skipped so huge/regenerable data is
        never uploaded.

  * WORKSPACE-TREE DISPLAY (zero filtering)
      server/src/utils/workspaceManager.js
      - The server-side SKIP_DIRECTORIES constant was DELETED entirely.
      - walkDirectory() no longer has any skip branch. It now returns 100% of
        what is on the server's disk for the project — every file and every
        folder, node_modules/.git/dist/build/.next included, at any depth.
      - getWorkspaceTree() and the /tree endpoint therefore reflect the real
        contents of the workspace exactly.

WHY THE WATCHER STILL BEHAVES (and is NOT a filter)
  server/src/utils/fileWatcher.js keeps NEVER_DESCEND_INTO = { node_modules,
  .git } ONLY to bound how deep chokidar reports live changes (watching every
  file in node_modules would swamp the process). It does NOT remove anything from
  the tree: the top-level addDir for node_modules still fires, so the debounced
  auto-refresh re-fetches the full tree and node_modules (with its contents)
  shows up. A comment was added to the constant making this explicit so it is not
  mistaken for a display filter again.

FIX: Freezing/lag when pasting files or folders (paste + auto-refresh)
================================================================================

STATUS: complete and verified. The severe freeze was NOT one bug — it was the
paste feature and the chokidar auto-refresh stacking three blocking costs. The
root causes were 1 and 2 below; 3 and 4 were confirmed/improved.

ROOT CAUSE 1 — duplicate tree fetch per paste (refresh budget doubled)
duplicateWorkspaceEntry (client/src/features/workspaceThunks.js) awaited a
MANUAL refreshWorkspaceTree() immediately after the POST /duplicate 201, and the
chokidar watcher ALSO saw the copied files and emitted workspace:treeChanged,
which the client turns into another refresh. So every paste fetched the whole
tree TWICE. Fixed by deleting the manual refetch and letting the watcher be the
single source of truth (one debounced treeChanged -> exactly one fetch).

ROOT CAUSE 2 — synchronous, blocking recursive copy (server froze)
workspaceManager.copyPathInWorkspace() -> copyDirectoryRecursive() used
fs.mkdirSync / fs.readdirSync / fs.copyFileSync in a recursive loop. Copying a
folder containing a node_modules-like tree held the Node.js event loop for the
ENTIRE copy, so the terminal and every other API call stalled — this is what
felt like "the whole app freezing". Fixed by converting the copy to fs.promises
(async) with a yield to the event loop every COPY_YIELD_BATCH (250) files.
copyPathInWorkspace is now async and the controller awaits it.

Also fixed while auditing the same freeze: getWorkspaceTree()/walkDirectory()
had the identical problem — a synchronous fs.readdirSync recursion that walked
EVERY file, and after the tree-fix above that includes all of node_modules on
every single auto-refresh. The walk is now async (fs.promises.readdir, which
yields between directories), and both callers (import + GET /tree) await it.
The tree is still 100% unfiltered — only the blocking characteristic changed.

ROOT CAUSE 3 — chokidar deep-watching node_modules: CONFIRMED NOT THE CAUSE
fileWatcher.js already refuses to descend into node_modules/.git: the custom
`ignored` function is true for anything strictly INSIDE them (so only the
top-level addDir/unlinkDir is watched), and the same isRelevant() filter is
re-applied to every event. No deep file watchers are registered. Verified live
below. A clarifying comment was added; no behaviour change was needed.

ROOT CAUSE 4 — Explorer re-rendered the entire tree on every refresh: IMPROVED
Every refresh built brand-new node objects, so React re-rendered every row even
when nothing in most branches changed — expensive once node_modules adds
thousands of rows.
  - toReduxTree() (client/src/utils/cloudTree.js) now does STRUCTURAL SHARING:
an unchanged node (same name/type/path/open state and identical child object
references) is returned as the PREVIOUS object, so whole subtrees keep identity.
  - The tree row is wrapped in React.memo (FileTree.jsx), and the Sidebar
callbacks passed into it (submitCreate, handleRename, requestDelete,
handleCancelCreate, reportError) are now useCallback-stable, so the shallow prop
comparison actually holds. An auto-refresh now re-renders only changed branches.

FIX: Freezes on delete / copy / paste — root causes found and eliminated
================================================================================

STATUS: complete and verified. Client oxlint 0/0 (64 files); vite build passes;
        node --check on every changed server file passes.

METHOD: audited the watcher, the server file operations and the client refresh
path, then measured them directly on a real workspace containing 3000 files under
node_modules. Temporary stress harness was used and then deleted.

THREE contributing root causes were found (not one):

RC1 (the hard freeze) — SYNCHRONOUS RECURSIVE DELETE
  server/src/utils/workspaceManager.js deleteFromWorkspace() used
  `fs.rmSync(dir, { recursive: true })` (and deleteWorkspaceFolder() the same).
  Removing a folder that contains node_modules blocked the Node event loop for
  the ENTIRE deletion — the server, every other API call and the terminal all
  froze until it finished. This is not a tree-refresh problem: it is a blocking
  filesystem call on the main thread.
  FIX: `await fsp.rm(path, { recursive: true, force: true })` (one call handles
  files and folders). deleteWorkspaceFolder() is now async too. rename/copy were
  audited in the same pass: `fs.renameSync` -> `await fsp.rename`,
  `fs.statSync`/`fs.existsSync` guards -> `await fsp.stat` / `fsp.access`, and
  uniqueNameInFolder() (the "(copy)" name picker) is now async instead of a
  sync existsSync loop. The recursive copy itself was already async with a
  250-file yield.
  MEASURED: deleting 3000 files took 685ms with 89 event-loop ticks DURING the
  delete (a sync rmSync yields ~0 ticks). The server stayed responsive.

RC2 — CHOKIDAR WATCHED FILE-HEAVY BUILD DIRS DEEPLY
  server/src/utils/fileWatcher.js already refused to descend into node_modules
  and .git, but dist / build / out / .next / .cache were watched recursively.
  Those hold thousands of regenerable files, so chokidar maintained watchers and
  processed events for all of them on every copy/build. The watcher also had no
  depth cap.
  FIX: NEVER_DESCEND_INTO now covers node_modules, .git, dist, build, out,
  .next and .cache (the folder's OWN addDir/unlinkDir is still reported, so the
  Explorer still updates when one appears or disappears — the tree walk itself
  has NO exclusions and still displays them). Added `depth: 12` as a hard cap,
  kept `ignoreInitial: true`, and kept the reference-counted one-watcher-per-
  projectId design (startWatchingProject reuses an existing entry, stopWatching/
  disconnect release refs, closeAllWatchers on shutdown) — audited and confirmed
  there is exactly one instance per project.
  MEASURED: 100 writes INSIDE node_modules produced 0 notifies at the watcher.

RC3 — EVERY UI ACTION CAUSED TWO FULL-TREE WALKS
  The client already refetches the tree directly after create/delete/rename/
  duplicate. The chokidar watcher ALSO saw the same fs writes and, after its
  750ms debounce, emitted workspace:treeChanged, which the client turned into a
  SECOND full GET /tree. With node_modules present each walk reads and sorts
  thousands of entries, so every delete/copy/paste did the expensive work twice.
  FIX: new `suppressWatcher(projectId, ms)` in fileWatcher.js. The controller
  calls it at the start of delete / rename / duplicate / create / save / import,
  opening a ~1600ms window; a debounced notify that fires inside the window is
  dropped (logged as "suppressed (own API change)"). External changes (terminal,
  npm install, git) never call it, so they still notify normally.
  NET: exactly ONE client tree refetch per UI action.
  MEASURED: a self-suppressed top-level write produced 0 notifies; after the
  window expired a write notified again (1).

AUDITED, NO DEFECT FOUND:
  - Duplicate socket listeners: client/src/hooks/useWorkspaceWatcher.js already
    attaches `workspace:treeChanged` inside a useEffect with a matching
    socket.off cleanup, a correct [projectId, source, dispatch] dependency array
    and a client-side 400ms debounce; the server reuses one watcher per id. No
    listener/leak duplication exists.
  - Explorer memoization: TreeNode was already React.memo and toReduxTree already
    does structural sharing, so unchanged subtrees keep identity. The tree
    selector `state.fileSystem.tree` returns a stable reference across unrelated
    Redux updates (Sidebar does not subscribe to terminal/ui/editor slices), so
    unrelated state never re-maps the Explorer. Hardened anyway: FileTree itself
    is now wrapped in memo, and the Sidebar callbacks it receives were
    stabilized (cut/copy/copy-path via useCallback; paste/request-create via
    refs mirrored in an effect so no stale closures and no ref-write during
    render).

REQUIRED BEHAVIOUR TESTED (real fs, 3000-file node_modules workspace):
  - Delete node_modules (folder): 685ms, non-blocking, gone from disk, tree no
    longer lists it.
  - Copy f.txt then paste into A, B and C in quick succession: 17ms total, all
    three files exist, tree lists A/B/C plus the renamed file — no reload.
  - Rename/move f.txt -> g.txt: reflected on disk and in the tree.
  - Watcher: node_modules-internal writes 0 notifies; top-level write 1; own
    suppressed change 0; resumes after the window.
  - Client verifies: oxlint 0/0 (64 files), vite build succeeds.

AI Code Editor — Phase 13: Automatic Key/Model Fallback on 429, Token-Lean
               Agent Prompts, Scratch -> Named Project Adoption

STATUS: complete and verified. Three fixes to the AI Agent system:

            saved keys and then the tool-capable models — the task keeps going;
        (2) the prompt sent to Groq each turn is trimmed so a simple task no

        (3) an empty "Scratch" workspace is renamed after the task into a real,

--------------------------------------------------------------------------------
1. AUTOMATIC KEY + MODEL FALLBACK ON 429
--------------------------------------------------------------------------------
THE CHAIN, IN ORDER (server/src/services/agentService.js)
  When an agent run starts, agentSocket resolves ALL of the caller's saved keys
  in preference order (explicit keyId first, then newest-first) via the new
  apiKeyService.resolveKeysForUser(ownerId, keyId). runAgent receives that list
  as `apiKeys` and builds a MODEL PLAN with resolveModelPlan(keys):
      * every saved key is asked for its live GET /models list;
      * the union is filtered through the existing TOOL_CAPABLE_MODELS allowlist
        (preferredModelOrder, so GROQ_MODEL still wins if set) -> the ordered
        list of models this user can actually run.
      * A key that cannot list models is skipped; only when NO key can list does
        the run fail with that key's error.
  For every chat completion, requestCompletion() tries, in this exact order:
      1. the currently-active model with the currently-active key;
      2. every REMAINING saved key on that SAME model (key 2, key 3 …);
      3. only then the NEXT model in the allowlist, again across all saved keys
         (model x key matrix).
  So "gpt-oss-120b rate-limited" walks gpt-oss-120b/key1 -> gpt-oss-120b/key2
  -> gpt-oss-120b/key3 -> llama-3.3-70b/key1 -> … -> llama-3.1-8b/keyN.

WHAT COUNTS AS "TRY THE NEXT ONE"
  - 429  -> rate limit: advance to the next key/model (the whole point).
  - 404  -> that model is not served by that key: skip just that pair.
  - 401/403 -> that key is rejected: skip that key.
  Any other status (5xx, network) is a real failure and is surfaced as before.

RETRY-AFTER RESPECTED
  callGroq attaches error.retryAfterMs by reading the standard `Retry-After`
  header (seconds OR an HTTP date) and/or Groq's own text ("Please try again in
  15.79s", "…in 1m30s"). After EVERY key/model pair has been tried and all were
  rate-limited, if the shortest suggested wait is <= 15s (MAX_FALLBACK_WAIT_MS),
  the agent emits a "waiting Ns before one retry" note, sleeps exactly that
  long, and retries the active combination ONCE. Only if that also fails (or the
  wait is long) does the run end. The FINAL error is exactly:
      "All available API keys/models are currently rate-limited. Please wait a
       moment and try again, or add another API key in Settings."
  and carries code RATE_LIMITED.

VISIBLE IN THE LIVE FEED + MODEL INDICATOR
  Every switch emits an `agent:action` event of type 'fallback' with a plain
  note ("Rate limit hit on openai/gpt-oss-120b with primary — switching to
  secondary…", "Rate limited on openai/gpt-oss-120b across saved keys —
  switching to llama-3.1-8b-instant…", "Recovered — now using …"). Each event
  also carries details.model, so the AIPanel header's model label updates to the
  combination actually in use at every point. The panel gained a RefreshCw icon
  for 'fallback' rows (and FolderCog for the rename row below).
  agentSocket no longer picks a single key: it passes the whole decrypted list
  and still drops every reference in `finally`.

--------------------------------------------------------------------------------
2. TOKEN-USAGE REDUCTION PER TURN
--------------------------------------------------------------------------------
  The loop still keeps the FULL canonical history in `messages`, but it now
  sends a TRIMMED view every turn via trimMessages():
    - the most recent 8 messages (KEEP_RECENT_MESSAGES) are sent untouched — the
      model always sees the immediate context in full;
    - older `role:'tool'` results longer than 400 chars are replaced with
      "[Older tool result omitted to save tokens (N chars). Re-run the tool if
      you need it again.]" — so a big read_file no longer rides along for 20
      more turns;
    - older assistant tool_calls have their arguments slimmed: create_file /
      edit_file file bodies are DROPPED, leaving only { path } (plus command for
      run_command). This is the single largest win, because a create_file call
      embeds the entire file in its arguments.
  Nothing is mutated on the canonical history (re-running a tool is always
  possible), and tool_call/tool pairing stays intact (we only shrink strings).
  Also reduced the per-result caps: MAX_TOOL_RESULT_CHARS 12000 -> 8000 and
  MAX_READ_CHARS 30000 -> 24000. The system prompt still carries only the
  dynamic tree context; no static repetition was added.
  Net effect: a basic HTML/CSS/JS todo task stays lean because each turn only
  pays for the last few turns plus the current tool result, not the whole run.

PART 1 — THE STATIC PREVIEW ROUTE (/preview/:projectId/*)
--------------------------------------------------------------------------------
Mounted at the app level in src/app.js (NOT under /api), so the URL is a clean

NEW SERVER FILES
  src/routes/preview.routes.js
    Two patterns — '/:projectId' (bare root) and '/:projectId/*' (everything
    else, captured in req.params[0]) — both behind the SAME guard chain:
      protectPreview -> validateProjectId -> authorizeProject -> ensureWorkspace
    The last three are the exact middlewares the /api/workspace routes use, so
    ownership and 'folder exists' semantics are identical.

  src/middlewares/protectPreview.js
    Reuses the existing JWT (jsonwebtoken + env.jwtSecret). Because a preview is
    opened as a PLAIN browser tab it cannot send the Authorization header, so
    the token is read from the `token` query parameter (and the Authorization
    header too, for programmatic callers). A missing/expired/forged token -> 401;
    a valid token sets req.user = { id } exactly like authMiddleware.protect.

  src/controllers/preview.controller.js
    - contentTypeFor(path): small built-in MIME map (html/htm, css, js/mjs/cjs/
      jsx, json/map, txt, xml, svg, png/jpg/jpeg/gif/webp/avif/bmp/ico, woff/
      woff2/ttf/otf/eot, mp3/wav/ogg, mp4/webm, pdf, wasm, zip); anything else is
      application/octet-stream. No new dependency.
    - servePreviewFile: resolves the request path with resolveWorkspaceFile()
      (the same traversal guard as every other workspace path builder), turns a
      directory (or empty path) into its index.html, 404s a missing file, and
      always sets Cache-Control: no-store + X-Content-Type-Options: nosniff so
      a reload shows the current bytes, never a cached copy.
    - HTML injection: for .html/.htm ONLY, the response body gets a small script
      inserted immediately before the closing </body> tag via a string replace
      (the file on disk is NEVER modified). If there is no closing </body>
      (malformed/fragment HTML) the script is appended at the end instead.
    - Binary safety: non-HTML files are read and sent as raw bytes (Buffer), so
      images/fonts survive byte-for-byte.

  src/utils/workspaceManager.js
    + resolveWorkspaceFile(projectId, relativePath) -> { root, absolute, relative }
      (reuses the private resolveInsideWorkspace guard; lets the preview read raw
      bytes instead of the UTF-8 decoded readFileFromWorkspace).

THE INJECTED LIVE-RELOAD SCRIPT
--------------------------------------------------------------------------------
Inside every served .html file, just before </body>:

    <script>
    (function () {
      var PROJECT_ID = "<projectId>";
      function connect() {
        var socket = window.io({ transports: ['websocket', 'polling'] });
        socket.on('connect', function () {
          socket.emit('preview:watch', { projectId: PROJECT_ID });
        });
        socket.on('preview:reload', function (p) {
          if (!p || p.projectId === PROJECT_ID) window.location.reload();
        });
      }
      var s = document.createElement('script');
      s.src = '/socket.io/socket.io.js';   // served by the SAME Socket.IO server
      s.async = true; s.onload = connect;
      document.body.appendChild(s);
    })();
    </script>

The Socket.IO client bundle is loaded from /socket.io/socket.io.js, which the
Socket.IO server already serves on its own origin. The preview page is served
by that same server, so the connection is same-origin — no CORS, no second URL.
The projectId is validated to [A-Za-z0-9_-] before it reaches here and is
JSON-encoded into the script.

PART 2 — LIVE RELOAD THROUGH THE EXISTING CHOKIDAR + SOCKET SYSTEM
--------------------------------------------------------------------------------
No new watcher was added. The one chokidar watcher per active project
(src/utils/fileWatcher.js, already used for Explorer auto-refresh) now drives
BOTH signals:

  - src/utils/fileWatcher.js
      startWatchingProject(projectId, notify, previewNotify) gained a second,
      optional notifier. Each relevant fs event schedules:
        scheduleNotify()          -> debounced 750ms -> notify()
        schedulePreviewReload()   -> debounced 350ms -> previewNotify()
      The preview timer is deliberately NOT gated by suppressWatcher(): a save
      made through our own API suppresses the redundant full-tree walk, but that
      save is EXACTLY the change a preview must reflect, so it still reloads.
      A burst of writes (8 saves in a row) collapses into ONE reload. Both timers
      are cleared in stopWatchingProject / closeAllWatchers.

  - src/socket/workspaceSocket.js
      One helper builds the watcher callbacks:
        treeChanged -> io.to('workspace:<id>').emit('workspace:treeChanged')
        preview     -> io.to('workspace:<id>').emit('preview:reload')

      SAME room and takes the SAME reference-counted watcher reference. That
      means a preview tab left open with no editor attached keeps the watcher —
      and therefore live reload — alive on its own. disconnect/workspace:unwatch
      release references exactly as before.

  FLOW: save style.css -> server writes the file -> chokidar 'change' -> the
  debounced preview timer fires -> preview:reload to the project room -> the
  injected script calls location.reload() -> the tab shows the new CSS, with no

1. ROOT CAUSE — THE NESTED "todo-app" FOLDER (issues #1 and #4)
--------------------------------------------------------------------------------
THE RENAME WAS NEVER A COPY. renameWorkspaceFolder() has always been a true
top-level fs.renameSync of the folder itself (workspaceManager.js), so contents
keep their relative positions. The real defect was TIMING + PATH, three parts:

  (a) THE CONTAINER CAME FIRST. POST /api/workspace/scratch ignored the task and
      always created/reused a folder literally named "Scratch", so every fresh
      agent task started its life inside a folder that was not the project.
  (b) THE RENAME COULD ONLY HAPPEN AFTER THE MODEL SPOKE. agentSocket renamed
      the folder when the model's first message contained a PROJECT_NAME line
      (and otherwise in `finally`, i.e. AFTER every tool call). A model's first
      message is very often tool_calls with content: null — extractProjectName()
      then returned null and the rename ran at the very end of the run.
  (c) THE MODEL NESTED ITS OWN NAME. Nothing told the model that the workspace
      root already IS the project folder, so it wrote paths prefixed with the
      name it had just chosen ("todo-app/index.html").

  Net effect, reproduced on the ORIGINAL code (tmp-fresh-task-test: 14/34):
      Scratch/task-tracker/{index.html,style.css,script.js}
  …and, when the name only arrived at the end, the rename produced the reported
  double:  task-tracker/task-tracker/*  — a project nested inside a copy of
  itself, with GET /preview/.../index.html answering 404 because the Explorer and
  the preview both expect the files at the project root.

THE FIX — the name is settled BEFORE the folder exists and BEFORE the first
file-write, and paths can never re-create the project's own name:

  server/src/controllers/workspace.controller.js
    POST /api/workspace/scratch now takes an optional { task }. With a task:
      * a FRESH workspace is created DIRECTLY under its final name (the
        backend-derived slug, chooseScratchProjectName/deriveProjectName) — no
        generic "Scratch" container is ever created;
      * an anonymous Scratch being reused for a task is renamed IN PLACE (still
        a true folder rename) before anything is written;
      * the response carries that real name with isScratch: false, because a
        workspace named after a task IS a real project from that moment.
      Without a task (Explorer "New File" with no project) the classic
      anonymous Scratch behaves exactly as before — verified 21/21 by the
      legacy tmp-create-test.

  client/src/services/api.js + features/workspaceThunks.js + features/aiSlice.js
    openScratchWorkspace({ task }) forwards the task; when the server answers
    with isScratch:false the thunk dispatches applyAgentProject, so the Explorer
    root label, the topbar chip and workspace.source ('cloud' -> Export/Sync)
    flip at OPEN time instead of waiting for a mid-run adoption.

  server/src/socket/agentSocket.js
    adopt(null) now runs BEFORE runAgent builds its prompt: any still-anonymous
    folder is renamed to the task slug before the first tool call. The model's
    PROJECT_NAME line can still rename it again (to a better name) on its first
    message — also before any tool executes — and `finally` remains the safety

    adoptScratchProject() is now idempotent and precise: it renames only when

1. THE 400 "Failed to parse tool call arguments as JSON" BUG
--------------------------------------------------------------------------------
ROOT CAUSE: when a model tried to emit a whole large file in ONE tool call, the
completion hit its (default) token ceiling and was cut off mid-JSON. Groq then
rejected the request with HTTP 400 (code tool_use_failed) BEFORE returning a
message, so the agent loop saw a non-retryable error and aborted the whole task.

FIX (server/src/services/agentService.js):
  - callGroq now sends an EXPLICIT max_completion_tokens (8192) so a long file
    write is not truncated mid-JSON in the first place.
  - A 400 whose message mentions tool-call parsing (tool_use_failed /
    failed_generation / "failed to parse tool call arguments") is classified by
    isToolCallParseError() as RECOVERABLE, not fatal.
  - On such an error the loop retries the SAME turn up to MAX_PARSE_RETRIES (2)
    times with the temperature LOWERED (0.2 -> 0.1 -> 0.0) and appends the
    corrective note: "Your last tool call had invalid JSON … create_file for the
    first part and append_to_file for the rest, keep each call under about 120
    lines, and properly escape quotes and newlines."
  - If it still fails, escalateAfterParseFailure() moves to the NEXT model in
    the fallback chain (and then the next key) with the SAME message history and
    keeps the task going instead of ending it.
  - Both recoveries stream to the live feed as a soft note ("Tool call was
    malformed, retrying with smaller chunks…") and a normal fallback row — no
    red fatal error.

CHUNKED WRITING (part 2): a NEW tool append_to_file(path, content) appends to an
EXISTING file (creating it when missing), backed by appendFileToWorkspace() in
utils/workspaceManager.js. The system prompt now REQUIRES files longer than about
120 lines to be written as create_file (part 1) + append_to_file (parts 2..n).
The streamed feed labels each append "Writing index.html (part 2)" (FilePlus2
icon). A whole large HTML/CSS/JS file must never go into one call.

--------------------------------------------------------------------------------
2. PLAN + CHECKLIST + VERIFY (the agent FINISHES the task)
--------------------------------------------------------------------------------
  - The system prompt makes the agent's FIRST message start with a
    "PLAN: file1, file2, …" line. extractPlanFiles() parses it and the plan is
    stored in the per-project backend session (agentSessionService).
  - Before accepting a final, tool-call-free "done" message, runAgent checks the
    PLAN against the real filesystem (existsInWorkspace). If any planned file is
    missing it sends the model "These planned files are still missing: […].
    Continue and create them." and continues the loop (up to 3 reminders).
  - The per-run tool-call cap was raised from 25 to 60 (MAX_TOOL_CALLS) so a
    multi-page site can finish; a safety cap still exists.
  - Vanilla HTML/CSS/JS prompt rules now require multi-page sites to be plain
    linked .html files sharing one style.css/script.js, Tailwind + icon
    libraries via CDN script tags (no build step), a plain-CSS replacement for
    any build-only library (e.g. Framer Motion) reported in the summary, and
    correct relative links between pages.

3. CONTINUE / RESUME (part 4)
--------------------------------------------------------------------------------
  - NEW server/src/services/agentSessionService.js keeps each project's message
    history (trimmed), its plan and framework in memory.
  - A run that ends in an error or hits the cap persists its session.
  - The AI panel shows a "Continue task" button when the last run ended that way;
    typing "continue" does the same. It re-runs with the saved history plus
    "Continue the previous task. First call list_directory … then finish the
    remaining files from the plan." The socket rejects a resume with no session
    (NO_SESSION).

--------------------------------------------------------------------------------
4. RATE LIMITS: WAIT, DON'T ABANDON (part 5)
--------------------------------------------------------------------------------
  - On 429 the Retry-After / "try again in Xs" value is read. When every key and
    model is rate-limited and the wait is <= 60s (MAX_FALLBACK_WAIT_MS), the
    agent waits it out with a LIVE 1-second countdown note ("Waiting 12s for
    rate limit to reset…") and retries the SAME request automatically. Only a
    longer wait, or exhausted retries, falls through to failure.
  - After each response the remaining-token headers are inspected; when less than
    ~10% of the per-minute token budget is left, the next request is paced a few
    seconds (a note is streamed) so large file writes do not burn out the budget.

--------------------------------------------------------------------------------
5. AI-BASED PROJECT NAMING (part 6, fixes "aapko-ek")
--------------------------------------------------------------------------------
  - The "first words of the prompt" fallback is GONE. At the start of a fresh
    scratch task the backend makes ONE small Groq call (temperature 0, tiny max
    tokens) that reads the request in any language (English / Urdu / Roman Urdu /
    Hinglish) and replies with a kebab-case name such as
    "three-page-static-website". The result is sanitized (lowercase a-z 0-9
    hyphen, max 40 chars) and collision-handled by the existing rename logic.
  - If that call fails, the name falls back to the SELECTED FRAMEWORK
    (html-project, react-project, next-project, …) — still never a prompt word.
  - openScratchWorkspace now always creates an anonymous Scratch; the socket
    renames it with the AI name (or the framework fallback) BEFORE the first
    file is written.
